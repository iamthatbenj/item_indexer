## Pending local input, not saved records

Item names, descriptions and current-keeper selections; existing story text; and new story text, storyteller selection and stable recording-request ID are retained in browser IndexedDB (`family-belongings-pending-text`, version 1). Each copy carries its initiating account, collection, item/optional story target, original expected version, local copy/revision IDs and local retention time. No session credentials, signed URLs, storage keys, recorder/editor identities or server-confirmed flags are stored. Local retention timestamps are not historical item/story dates.

Typing attempts local retention without a server write. The UI reports retaining the latest input until that specific revision commits; an older queued write cannot falsely announce that newer input has been retained. A local-retention message follows the IndexedDB commit, not merely scheduling it. An immediate browser/process/device interruption before that asynchronous commit can still lose input. Keep important originals separately. If storage is unavailable, input remains usable on the open page and saving online is still allowed, but a warning asks for a separate copy before leaving/reloading; the application does not pretend local retention succeeded.

After reload/navigation, current saved fields appear first. **Resume pending text** deliberately loads a selected local copy, never automatically replaces server-rendered fields, saves, merges or advances an expected version. Existing item/story recovery retains the original expected version and opens the ordinary conflict comparison. While a local resume/discard is still loading, editable fields, save buttons and comparison controls are unavailable; native form submission is also guarded so it cannot submit the previous fields or clear the selected pending copy before restoration finishes. Contributors must load the current persisted content and explicitly choose **Revise against version N** before saving; further intervening changes conflict again. Missing targets cannot be reviewed or edited into existence. Keeper/storyteller references are validated against current collection records during the normal server save.

New stories retain the original recording-request ID through interruption and recovery. A lost successful response retries that same request: the existing creation hash/idempotency check returns success rather than inserting another story or replacing an edited story. Changed text for an already-saved request conflicts; inspect the saved story and deliberately use its existing editor rather than inventing an automatic duplicate or overwrite.

## Matching copies and cleanup

Each editor has its own working-copy ID. Resuming creates a separate working copy while keeping the source until confirmed save/discard, so two tabs resuming one copy cannot clobber each other's later local input. Lists can therefore contain both the original pending copy and resumed work. A confirmed server save clears only the matching working copy and immediately resumed source revisions. Older independent copies from earlier interrupted sessions can remain for deliberate review/discard; there is no content-based purge. A changed revision, another editor's copy, different item/story or other collection remains intact. Discard removes only the selected exact local revision and cannot undo any server save. Discarding this editor's working copy resets its fields to the current server-provided initial values and detaches its source association without deleting that original pending copy. A subsequent independent save cannot clean up the detached original. Discarding a different copy leaves current input alone.

A failed/ambiguous server save retains pending input; no success state is inferred from a local commit. If server success is confirmed but local cleanup fails, the UI explicitly distinguishes these facts and keeps the same version/request context. Existing edits can reconcile a no-op against current saved content; new stories retry the same request. No destructive history rewrite, automatic semantic merge or editorial privilege is added.

## Account isolation and unavailable targets

The editors and local-copy viewer receive only account/target IDs from authenticated server pages. A fresh private/no-store account check gates local reads, previews/actions and server-save initiation. Focus, visibility, unmount and cross-tab identity notifications invalidate asynchronous work by generation. Delayed successful identity or IndexedDB results cannot reauthorize the UI, expose prior input or perform later local writes/deletes. Cross-tab notifications share the #13 identity channel but can only hide, never grant access. A different account's values are not rendered into the editable UI. Same-profile developer tools or same-origin script access are not an encryption boundary; use separate browser/OS profiles on shared devices.

Browser save requests also pin the initiating account ID, checked before item/story writes. A 401 or account-pin mismatch response invalidates/hides the old local UI and notifies other local-privacy components, covering session changes after a successful preflight identity check. This is not authorization: actual sessions, current membership, original fixed target, collection-scoped references and expected versions remain authoritative. Legacy requests without the pin retain the authenticated server protocol. Existing storyteller/original recording credit stays immutable during editing; editing identity comes from the actual session, never the pending copy.

`/pending-text`, linked from Family collections and editor pending controls, lets the freshly authenticated original account inspect/copy or discard its own local input even when the collection/item/story is no longer accessible. It does not read unavailable server records, reinstate membership, restore photos or recreate stories. Opening an original editor still runs its ordinary access/target checks. Record-removal actions are not implemented yet: the missing-story regression simulates a hard-absent target in the disposable database, not a shipped delete permission or recovery workflow. Future removal/tombstone work must preserve these boundaries, including new-story idempotency for removed saved requests.

## Practical persistence limits

- At most **25 drafts / 1 MiB per account and collection**, enforced inside the local write transaction; earlier pending input is never silently evicted by the application. Browser quotas may fail earlier. This is not a device-wide or service billing quota.
- No full offline editing/browsing, background sync or guaranteed camera-style offline entry. Initial account checks and server pages need connectivity; already-open, verified editors can attempt local retention during a temporary failed connection. Reconnection never starts server saves automatically.
- Browser eviction, private-browsing closure, clearing site data, changing origins/profiles, device loss or failed local commits can remove copies. There is no indefinite-retention or browser-persistence guarantee. Local plaintext can be sensitive; separate browser profiles and separate copies remain necessary.
- Unconfirmed local input is not preservation/archive content. No persistent server field, schema, retained-file relationship or R2 behavior is added. The established photo optimization/metadata and private-storage ADRs are unchanged.

npm run build

Twenty-three new journeys inspect real browser IndexedDB and disposable database artifacts through public UI/network behavior: reload/navigation and keeper recovery; repeated stale item/story reconciliation; new-story lost acknowledgements; temporary failed connections; absent stories; session expiry/revoked membership; unavailable storage; independent-tab cleanup; delayed identity/storage results across accounts; confirmed saves with failed local cleanup; expired/replaced sessions between successful verification and the real pinned POST; and queued local writes whose latest revision has not committed yet. Held-storage regressions also verify that all three forms stay disabled and ignore native submission until local restoration completes. Pre-review validation: **169 browser/integration tests passed in one clean full run (35.1 minutes)**, including the initial 20 text-recovery cases. The required pre-commit review then found that discarding a resumed working copy left its source linked to a later unrelated save. Three added browser regressions reproduced deletion of the original after that later save in item, story and new-story forms. Discard now clears that association without deleting the original; the complete **23-case text-recovery suite passed (4.7 minutes)** after the fix, followed by fresh typecheck and production build. The expanded 172-case full suite has not been rerun. Typegen/TypeScript, production webpack build, production dependency audit (zero vulnerabilities), nine hook regressions and diff checks also passed. These are local automated results, not authenticated hosted/mobile acceptance; mocks of internal authorization/transaction functions are not acceptance evidence.

An initial broader run exposed a photo pending-list assertion that inspected unhydrated SSR UI, and a zero-timeout fixture write racing live file-database reads, with later fixtures failing on the resulting lock. Photo fixtures now wait for the same 30-second native client-readiness boundary as camera tests after collection creation, navigation and reload, not merely an SSR heading. The relevant direct file-database fixtures use the driver's 5-second busy timeout for all pooled connections (rather than a PRAGMA on one connection), and retained-image requests drain before photo fixture resets. A 15-case sequence of camera/library capture, lost acknowledgement, expiry and fixed-target recovery passed across three repetitions. The malformed-comparison fixture also waits for the stale save POST to complete before installing a one-use GET interceptor, so the POST cannot consume that interceptor; this check passed three repetitions. The full photo suite then passed 40 cases across two complete repetitions with the centralized readiness boundary. No production database configuration or authorization behavior was relaxed for these fixture fixes.

No migration, capture pause, provider resource or secret is required. Rollback to #13 leaves server records/history and browser pending-text bytes intact but hides the new recovery UI. Do not clear site storage as a rollback step; a compatible release is needed to inspect/resume those copies. Application rollback cannot recover browser-evicted input.
