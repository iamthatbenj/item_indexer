# Resume interrupted photo capture

Scope: [#13](https://github.com/iamthatbenj/item_indexer/issues/13), following [draft capture](photo-drafts.md) and [multiple views](item-photos.md). Explicitly resume or discard a locally retained pending photo, without creating a second item/file relationship after uncertain success. This is not background synchronization, full offline capture/editing, offline browsing, or a backup.

## Local pending versus saved

Camera/library selection commits a `File`, stable random operation UUID, initiating account ID, collection ID, optional fixed item ID/display name and selection time to IndexedDB (`family-belongings-pending-photos`, version 1). These commit together **before** any upload request. No signed URLs, storage keys/credentials, session cookies or server-confirmed flags are stored there. A preview URL exists only in memory and is revoked when the selection changes or is hidden.

The fresh account check requires a connection before a new selection can be durably staged. If that check is unavailable, no upload starts and the contributor must keep the original and reselect after reconnection; capture while already offline is not guaranteed. Once locally retained, interrupted photos can survive reload subject to browser limitations below. The pending list is scoped to the signed-in account and current collection. An item page narrows it to that item; a collection page also lists pending additional views with their original item labels. Resume prepares the stored photo for deliberate Save/Retry; no upload runs automatically on mount, reload, focus, or restored connectivity. Selecting another photo is a new operation, not a retry of earlier work; earlier pending entries remain available. Saving a pending additional view from the collection page targets its original item, never a new draft or another collection.

**Pending means save not confirmed**, not proof of server failure. A lost response can leave both a saved item in Belongings and a pending local copy. Retry always begins with the same operation UUID/size/target. The server returns the original saved destination before authorizing any further upload when that operation has succeeded. A valid fixed-destination acknowledgement removes the local copy, then navigates to the saved item or refreshes its photo views without replacing unsaved item text. Failed local cleanup explicitly reports server-confirmed success and retains the same operation for a later check/discard.

Discard deletes only that account/collection/operation's local copy. It does not cancel an in-flight request in another tab, erase a server save, remove a photo, or delete a staged/retained object. Check Belongings before treating ambiguous work as unsaved. New selection intentionally allows another record even for identical bytes; content hashes do not deduplicate different family contributions.

## Authorization and privacy

The server-rendered component receives the account ID, not a session credential. Before reading/exposing local pending entries or previews and before selection/resume/save/discard, a private/no-store `GET /auth/account` confirms the current session matches that account. Focus/visibility changes hide and recheck pending UI. A BroadcastChannel identity notification can only hide another tab’s pending UI, never grant access; all reads/actions still require the fresh server check. A Check account and pending photos button permits explicit reconnection without starting an upload. A changed/expired identity hides the old pending list and selected preview and asks for the original contributor to sign in. Browser storage remains scoped by account **and** collection, not email or a shared last-active collection.

Every asynchronous capture operation carries a verification generation. An account-change notification, focus/visibility transition or unmount invalidates outstanding results; delayed successful identity responses cannot reauthorize the UI or broadcast an obsolete identity. Queue reads are checked again after IndexedDB completes, and pending writes/deletes check the generation after opening storage (and before a delayed retention write). Upload responses are checked before any next step, local cleanup or navigation. Work already issued can still finish, but invalidated operations do not start subsequent work or expose old local data; explicitly check the account and resume the same operation to reconcile uncertain saves.

New browser begin/finish forms also pin `accountId`; a changed signed-in account receives 409 before server upload work. This closes the check-to-begin identity race. Legacy requests without the field retain the existing authenticated protocol. The field is not authorization: all server writes still check the actual session, fresh collection membership, uploader ownership, target item and processing lease; publication rechecks access after storage I/O. There are no new editorial/admin privileges. Already-issued short-lived upload/download authorizations cannot be recalled. No service worker or public-cache path is added.

Local storage is **not encrypted account storage**. It can contain original hidden photo metadata, filenames and full camera bytes until saved/discarded/evicted. The application hides it from other signed-in identities; this is not protection against another person controlling the browser profile, developer tools, same-origin script execution or the device. Use separate browser/OS profiles on shared devices, retain originals elsewhere, and discard unneeded pending copies. Stored previews are not copied into HTML/localStorage or uploaded to a different identity's collection.

## Limits and failure behavior

- Existing input limits still apply: nonempty files up to 20 MiB; server actual-content/pixel validation, orientation, colour and metadata stripping remain unchanged. Unsupported input remains unconfirmed/pending with format guidance; discard it and select a supported image.
- Local staging allows at most **10 photos / 80 MiB per account/collection**, checked in one read/write transaction. There is no silent eviction by the application. Browser quotas may reject much earlier; this is not a total-device or service billing cap.
- An unavailable/denied IndexedDB, quota failure, failed transaction or failed local write blocks new upload work. The open selection remains available where possible for retry, with guidance to keep the original and free/enable storage or discard unnecessary pending copies. The UI never claims durable local retention after a failed write.
- Browsers can evict data under storage pressure, clear it when site data is removed, or discard private-browsing data when the private session ends. Device loss, profile changes and origin changes do not transfer pending copies. No fixed retention duration or browser-persistence guarantee is made. This slice does not request persistent-storage permission or depend on StorageManager support.
- Expired sessions require original-account authentication. Removed collection membership, missing item targets, rate/capacity limits, processing leases and storage/service failures keep pending copies rather than changing targets. A signed-in original contributor can discard a local copy after membership removal from an already open capture page; this grants no server access. Re-entry to an inaccessible collection is not offered.
- Upload intents still have 15-minute validity, PUT URLs at most 120 seconds and processing leases at most 120 seconds. Beginning an **expired unsaved** operation renews that same intent only after checking original account/collection/item/size, current membership, request allowance and absence of a live processing lease. Saved intent replays return durable success first, regardless of expiry. Finish alone still rejects expired unsaved intents; retry starts with begin/renew and reuploads retained bytes. No live worker is displaced by renewal.

## Preservation and deployment

No server schema, migration, persistent server field or retained-file relationship is added. The existing private R2 bucket, CORS, staging-only one-day lifecycle, processing limits and credentials remain unchanged. Local unconfirmed originals are **not** server preservation content; future portable archives include only the retained photos and established relationships/provenance, not IndexedDB copies, temporary upload intents, signed URLs or raw originals. Existing archive and backup boundaries remain intact.

Local implementation only. No push, deployment or production changes have been performed for #13. No capture pause is needed for a compatible deployment. Rollback to #12 preserves server records/files and browser IndexedDB copies, but hides resume/discard UI and cannot renew expired intents. Do not clear browser/site storage as a rollback step; return to a compatible release to resume. Application rollback is not recovery of browser-evicted bytes. Retain the server schema/data and prefer fix-forward.

## Verification

```sh
npm test -- tests/pending-photos.spec.ts tests/photo-drafts.spec.ts tests/item-photos.spec.ts

npm run typecheck
npm run build
npm audit --omit=dev
node --test tests/pre-commit-review.test.mjs

```

Twenty dedicated behavioral tests exercise browser IndexedDB plus real disposable libSQL and private S3-compatible storage: interruption before intent and during PUT; expired-intent renewal; lost successful finish response followed by reload; fixed additional-view/collection targets; changed account/stale tab; expired session and reauthentication; real rate rejection and removed membership; unsupported content/publication failure; unavailable browser storage; concurrent tab retry and mobile layout. Durable operation/item/photo identities, actual private retained object keys and SHA-256 are checked for duplicates. Network interruption and browser-storage failures are injected at public network/browser seams, not by mocking internal authorization/transaction functions. Seven additional races hold successful identity responses during Resume, Reconnect, Select, Discard and Save, or hold a real IndexedDB connection during Reconnect/Discard, then switch accounts in another tab. They assert that releasing old results neither reveals filenames/previews nor modifies old pending copies or begins server uploads. These mounted-client regressions suppress only development HMR messages after initial hydration so a development reload cannot mask the race.

Validation: after resolving the required pre-commit review finding, the final full Chromium/browser/integration run passed **149 tests (28.7 minutes)**, including all 20 pending-photo cases. The review identified a delayed successful identity response that could undo a cross-account hiding notification. A held-response browser regression reproduced the old preview reappearing; generation checks now invalidate all later UI/storage/upload steps, with the seven regression cases above also passing in a separate focused 20-test run. Typegen/TypeScript, production webpack build, production dependency audit (zero vulnerabilities), nine hook regressions and diff checks passed. The expiry browser case also passed three consecutive focused runs. Initial verification exposed a native-form hydration wait shorter than other camera tests; it now uses the same 30-second readiness allowance, without enabling unhydrated controls. A separate failure reproduced native libSQL lock contention when the synthetic populated-migration fixtures rebuilt tables while a capture page was making identity/preview reads. Those fixtures now leave capture before out-of-process schema work (including migration reruns), retaining their public behavior, atomic rollback and durable-artifact assertions. The originally failing migration passed five consecutive repetitions after this boundary fix; all six populated migration cases then passed twice, followed by the clean full run. No production database change or authorization relaxation was used to resolve these test issues.

Local validation is not hosted/mobile-browser acceptance. After rollout approval, use disposable photos on actual iOS Safari and Android Chrome to:

1. Select a camera/library image; interrupt before upload, during PUT and during processing. Reload/reopen and explicitly resume. Confirm one item/view and correct original target; check the collection list before retrying uncertain success.
2. Sign out and use a different identity in the same browser, including a stale tab; confirm no old pending filenames/previews appear. Sign back into the original account and resume. Try session expiry, removed membership and the busy/limited response without changing target.
3. Discard a pending copy, including one whose save was already successful. Confirm saved records/files remain unchanged.
4. Try private browsing, restricted/full storage, clearing site data and browser eviction behavior. Verify actionable messaging, lack of a false saved label and no promise that the pending original survives. Keep separate source copies; do not use sole-copy family material.
5. Check camera formats (including HEIC guidance), screen-reader/keyboard controls, long filenames, touch layout, storage impact and real R2/Vercel processing. Record browser/device versions and observed limitations; headless Chromium cannot establish Safari storage persistence or physical-camera behavior.
